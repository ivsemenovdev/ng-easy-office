## Общая оценка

Схема для v0.1 выглядит **логичной и читаемой**: география → больницы → отделения → оборудование, отдельно глобальный справочник видов и отдельно акты из DOCX. Миграции версионированы, FK в основном расставлены правильно, индексы на FK есть.

Ниже — замечания по приоритету.

---

## Критичные / архитектурные

### 1. Два параллельных «мира» оборудования

`equipment` и `diagnostic_acts` **не связаны FK**. Это осознанное решение (импорт из DOCX), но даёт последствия:

- один и тот же серийный номер может быть в акте и в справочнике без связи;
- нельзя построить историю обслуживания по конкретной единице оборудования;
- отчёты «акты ↔ парк оборудования» потребуют эвристик (по `serial_number` / названию).

**Варианты на будущее:** nullable `equipment_id` в `diagnostic_acts` + поля из DOCX как snapshot; или отдельная таблица связи `diagnostic_act_equipment`.

### 2. `is_active` есть, но API делает hard DELETE

У `hospitals`, `departments`, `equipment`, `equipment_types` есть `is_active`, но сервисы удаляют строки через `DELETE`. Получается смешанная модель:

- деактивация через флаг возможна, но не используется как основной путь;
- удаление отделения **каскадом уничтожает** всё оборудование (`ON DELETE CASCADE`);
- удаление вида оборудования блокируется FK (`RESTRICT`) — это правильно, но противоречит идее «мягкого» удаления через `is_active`.

**Рекомендация:** либо перейти на soft delete в API, либо убрать `is_active` там, где он не нужен.

### 3. Противоречивые политики удаления больницы

```text
hospitals → diagnostic_acts     ON DELETE RESTRICT  (нельзя удалить больницу с актами)
hospitals → departments         ON DELETE CASCADE   (отделения удалятся вместе с больницей)
```

На практике удаление больницы всё равно заблокирует `RESTRICT` от актов. CASCADE на отделениях сработает только после ручного удаления актов — это неочевидно и может привести к **массовой потере** отделений и оборудования одним DELETE.

## Средний приоритет (целостность данных)

### 4. Нет уникальности там, где она часто нужна

| Таблица | Что отсутствует |
|---------|-----------------|
| `departments` | `UNIQUE (hospital_id, name)` — дубли отделений в одной больнице |
| `departments` | `UNIQUE (hospital_id, code)` WHERE code IS NOT NULL |
| `equipment` | уникальность `serial_number` / `inventory_number` (хотя бы в рамках отделения или больницы) |
| `hospitals` | `UNIQUE (region_id, name)` — дубли названий в регионе |
| `diagnostic_acts` | любая уникальность — **дубликаты разрешены намеренно** |

### 5. `hospitals.region_id` без проверки уровня региона

Больница может быть привязана к любому `geo_regions`, не только к `federal_subject`. В сиде все 89 субъектов — верхний уровень, но ограничения в DDL нет. При появлении районов/городов возможны некорректные привязки.

### 6. Разная длина `serial_number`

- `diagnostic_acts.serial_number` — `VARCHAR(100)`
- `equipment.serial_number` — `VARCHAR(50)`

При попытке «связать» данные по серийнику возможны обрезания или несовпадения.

### 7. `equipment_types.name` — UNIQUE без нормализации

PostgreSQL сравнивает `TEXT` **с учётом регистра**: «МРТ» и «мрт» — разные записи. Trim на уровне БД тоже не enforced — только в UI/API.

### 8. Нет проверки `equipment_type_id` на активность

Можно создать `equipment` с `equipment_type_id`, у которого `is_active = false`. FK проверяет только существование записи.

## Низкий приоритет (качество схемы / эксплуатация)

### 9. `updated_at` не централизован

Поле есть почти везде, но обновляется **только в UPDATE-запросах сервисов** — триггеров нет. Прямые SQL-правки или забытый `updated_at = NOW()` в новом коде дадут рассинхрон.

`geo_countries` вообще **без** `created_at` / `updated_at`, в отличие от `geo_regions`.

### 10. Дублирование адресов

- `hospitals.address` — операционный
- `hospital_requisites.legal_address` / `postal_address` — юридические

Разделение задокументировано, но данные могут расходиться без синхронизации.

### 11. Недостающие индексы для типичных запросов

- `diagnostic_acts(act_date)`, `(hospital_id, act_date)` — для списков/фильтров актов;
- `equipment(serial_number)` — для поиска по серийнику;
- `departments(is_active)` partial index — по аналогии с `hospitals`.

### 12. Реквизиты: валидация только в API

`inn`, `kpp`, `ogrn` проверяются Zod в [`validation.ts`](backend/src/validation.ts), но **CHECK в БД нет**. Обход API (psql, другой клиент) позволит записать мусор.

### 13. Документация политики БД устарела

[`database-policy.md`](docs/ai/database-policy.md) упоминает миграции `001`–`007` и не перечисляет права `ng_app` на `equipment_types`, `departments`, `equipment` (миграция `009`).

## Что сделано хорошо

- Чёткое разделение справочников и операционных данных.
- Журнал `schema_migrations` + роли `ng_migrator` / `ng_app`.
- `hospital_requisites` как 1:1 extension — правильный паттерн.
- Индексы на всех FK в новых таблицах (`008`).
- Partial index `hospitals_active_idx` — хороший приём.
- `manufacture_year` с CHECK — единственное бизнес-ограничение на уровне БД в домене оборудования.
- ER-диаграмма в [`database-er-diagram.md`](docs/ai/database-er-diagram.md) отражает реальную схему.
